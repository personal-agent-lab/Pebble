# Pebble 第一版需求规格

## 1. 产品目标

构建一个持续运行、可成长、具备跨工具执行能力的个人 Agent。它能够在个人资料、邮件、日历和持久规则之间共享上下文，并通过用户确认安全完成真实事务。

## 2. 第一版范围

本文将 Rule/Memory 统称为“持久规则”，将 Skill/Workflow 统称为“Skill”。

| 项目项   | 约定                                                         |
| -------- | ------------------------------------------------------------ |
| 部署方式 | 单用户单实例部署，由单个 Agent 组织工具调用；凭证、规则与任务状态在该实例内持久化。 |
| 主要交互 | 对话式交互，支持 PC 和手机浏览器发起任务、查看进度、编辑草稿和确认操作；任务不依赖始终开启的浏览器页面。 |
| 个人资料 | 持久化保存、索引和检索资料；支持资料更新；回答与执行决策可定位到来源。 |
| 邮件     | 接入 Gmail；支持持续检查新邮件、搜索和读取邮件及完整往来、读取附件、准备回复或主动新写邮件、上传本地附件、编辑草稿并在用户确认后发送；重复检查不得重复处理或发送同一封邮件。 |
| 外部服务 | 首版接入 iCloud Calendar；支持日程查询、冲突检查和事件创建。外部写操作遵守第 3 节的确认要求。 |
| 能力组合 | Gmail、个人资料、iCloud Calendar 与持久规则和 Skill 共享任务上下文，可完成跨工具完整任务。 |
| 能力成长 | 用户纠正持久化为可读、可改的持久规则；反复成功的流程可沉淀为 Skill；自主沉淀的 Skill 须经用户审核确认后才能投入生产，已生效内容在新会话中继续应用。 |
| 安全原则 | 具有副作用的外部写操作必须先展示关键内容及影响，并获得用户明确确认后执行。 |
| 可维护性 | 核心规则、Skill 与关键配置保持可读、可修改，并通过 Git 管理版本。 |

## 3. 任务执行约束

### 3.1 自主决策与上下文共享

Agent 根据用户意图组合个人上下文和不同工具完成任务，而不是让用户逐个调用功能。

在本规格约定的范围内，处理动作、工具组合、执行后的后续处理，以及规则和 Skill 的沉淀时机与内容，均由模型自主判断，不预设固定业务处理流程。模型决策仍须遵守外部写操作确认、信息不明确时追问和邮件去重等约束。

### 3.2 持续运行与多端 Web 交互

系统持续检查新邮件，任务执行不依赖始终开启的浏览器页面。PC 网页端和手机网页端均为首版交付范围，采用响应式 Web 界面，按屏幕尺寸适配布局。两端均支持发起任务、查看进度与来源、编辑草稿、确认操作，以及资料、持久规则和 Skill 的查看、编辑与审阅。

### 3.3 外部写操作确认

具有副作用的外部写操作必须展示关键内容及实际影响，并获得用户明确确认。统一遵循：

```text
准备内容 → 展示预览 → 用户明确确认 → 执行
Prepare → Preview → Confirm → Execute
```

- 日程预览、邮件草稿及其最终确认内容必须持久保存；用户关闭或刷新页面后仍可查看和编辑待确认内容。
- 用户完成编辑后，对最终预览内容明确确认即可执行。
- 日程创建与邮件发送分别确认，执行内容必须与对应确认内容一致。
- 内容修改后，原有确认不再适用于修改后的版本。

### 3.4 执行结果

根据实际工具结果准确反馈执行情况。例如日程已创建但邮件发送失败时，应分别说明，不能将整个任务报告为成功。

## 4. 核心能力

### 4.1 个人资料

- 支持用户资料的持久化保存、索引、检索和更新。
- 回答与执行决策所依据的资料可定位到原文来源。

### 4.2 Gmail

- 能够持续获取新邮件，而不是仅在用户主动查询时临时读取。
- 新邮件同步后自动启动 Agent 处理，由模型判断邮件内容并决定后续处理动作；涉及外部写操作时仍需用户明确确认。
- 处理当前邮件时，应能关联同一线程或相关历史往来。
- 能读取邮件中的附件原始内容，附件不作为大段编码文本塞入工具输出。
- 用户在 Pebble 上传的本地文件可作为外发附件；附件内容不可变，并与被确认的草稿版本严格绑定。
- 回复和主动新写邮件都采用“生成草稿 → 用户编辑/审阅 → 明确确认 → 发送”的流程。
- 草稿作为完整卡片显示在 Agent 生成它的对话位置；用户可直接编辑，也可针对同一张卡片提出修改要求，修改不新建第二张卡片。
- 保存邮件处理及发送记录，重复检查不得重复处理或发送同一封邮件；重复确认不得重复发送同一项邮件操作。
- 发送结果不确定时，应先核实实际结果，不得直接再次发送。

### 4.3 iCloud Calendar

- 查询日程
- 检查时间冲突
- 生成日程预览
- 用户确认后创建事件

### 4.4 能力成长

#### 沉淀与复用

- 用户纠正：沉淀为持久规则，例如字段解释、偏好、确认习惯等。
- 成功流程：对于重复出现且稳定成功的任务，将处理流程沉淀为可读、可改的 Skill。
- 规则与 Skill 既可以由模型自主判断并沉淀，也可以由用户明确触发；沉淀后的内容仍须遵守本规格的执行约束。

#### 自主沉淀 Skill 的审核

- 自主沉淀的 Skill 先保存为草稿，Agent 应在对话中提示用户查看。草稿须展示触发词、必要参数、执行流程及安全性信息，包括涉及的工具、外部副作用和确认要求。
- 用户可审阅、修改草稿；只有用户明确确认最终草稿中的触发词、必要参数及安全性等信息后，该 Skill 才能投入生产。未经确认的草稿不得被 Agent 应用或执行，在新会话中同样不得生效。
- Skill 投入生产的确认不替代执行时对具体外部写操作的确认。

#### 持续生效与版本管理

- 已生效的规则和 Skill 在新会话中继续应用，并允许用户检查和修改。
- 规则与 Skill 通过 Git 管理，能够查看版本变化和回退。

## 5. 端到端验证场景

以下场景用于验证能力组合与执行约束，不将其步骤固化为所有任务的业务处理流程。

> 用户说：“帮我处理这封活动邀请。”Agent 需要从邮件理解任务，并综合个人资料和日历状态，最终在用户确认后完成日程创建和邮件回复。

新活动邀请邮件同步后，也应自动启动 Agent 处理，按同样的约束完成以下场景。

1. 读取并解析指定 Gmail 邮件，识别活动名称、时间、地点、组织者、回复要求等信息。
2. 关联相关邮件线程和历史往来，补充当前邮件缺失的上下文。
3. 检索个人资料和持久规则，获得与该任务相关的信息或偏好。
4. 查询 iCloud Calendar，检查目标时间是否已有冲突。
5. 若存在缺失信息、歧义或冲突，在对话中向用户追问，而不是自行猜测。
6. 生成“日程预览”和“邮件回复草稿”，将关键字段和实际副作用明确展示给用户。
7. 允许用户分别编辑日程信息和邮件草稿。
8. 按对应的最终确认内容创建 iCloud Calendar 事件、发送 Gmail 回复；每项操作分别遵守第 3.3 节的确认要求。
9. 在对话中准确报告执行结果，并将关键来源和执行结果归档到个人资料中。

## 6. 验收标准

以下标准共同构成第一版验收要求。

### 6.1 完整任务与持续运行

- 分别从 PC 和手机浏览器完整完成第 5 节场景，不依赖命令行终端或手工修改数据库。
- 两端布局适配各自屏幕尺寸，任务进度、来源、编辑字段和确认操作均可正常查看和使用；资料、持久规则和 Skill 的相关操作在两端均可完成。
- 在同一任务中组合 Gmail、个人资料和 iCloud Calendar，并共享必要上下文。
- 新邮件同步后，无需用户主动请求即可启动 Agent 处理；外部写操作仍等待明确确认。
- 任务不依赖始终开启的浏览器页面；关闭或刷新页面后，仍能查看和编辑已保存的待确认日程预览及邮件草稿。
- 场景完成后，关键来源和执行结果已归档；回答与执行决策所依据的个人资料可定位到原文。

### 6.2 确认与执行一致性

- 遇到缺失字段、时间冲突或含义不明确时追问，不使用未经验证的猜测执行写操作。
- 日程创建和邮件发送均展示清晰预览，并分别获得用户明确确认。
- 实际执行内容与对应的最终确认内容一致；修改后的版本不能沿用旧确认执行。
- 任务部分成功、部分失败时，在对话中准确说明各项操作的实际情况。

### 6.3 邮件去重与结果核实

- 重复检查邮箱不会重复处理或发送同一封邮件。
- 重复确认不会重复发送同一项已完成的邮件操作。
- 发送结果不确定时先核实实际结果，不直接再次发送。

### 6.4 能力成长与版本管理

- 用户纠正能够持久化，并在新会话中再次影响 Agent 行为。
- 至少一个成功流程沉淀为可读、可改、可版本管理的 Skill；已生效的规则与 Skill 在新会话中继续应用。
- 规则与 Skill 的沉淀同时支持模型自主发起和用户明确触发。
- 自主沉淀 Skill 后，在对话中提示用户查看草稿；用户能够审阅、修改触发词、必要参数、执行流程及安全性信息。
- 未经确认的 Skill 草稿在当前会话和新会话中均不得被应用或执行；明确确认最终草稿后才能投入使用，具体外部写操作仍单独确认。
- 用户能够检查和修改规则与 Skill，并通过 Git 查看版本变化和回退；关键配置通过 Git 管理版本。
