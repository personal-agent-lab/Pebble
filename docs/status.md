## 3. 已知偏差与未完成

- 远程访问只做了本机验证（身份头、来源校验、工具端点隔离与前端托管）；还没有用手机在外网经 Tailscale 完整走通两个场景，也没有实测 Serve 会清掉客户端伪造的身份头。
- Vite 开发服务器开放局域网且不做访问控制，只能配合 `PEBBLE_AUTH=off` 在开发时使用。
- 触发源插孔仍带邮件域名（`MailSource`、`accept_new_mail`、`create_app(mail_source=...)`），与“通用层不持有域措辞”的约定不一致；第二个触发源接入时改为域中立命名。
- 联网查询的来源没有独立呈现：`agent/client.py` 的流只取 `TextBlock`，`WebSearch` 结果里的 `Links` 和 `WebFetch` 实际抓取的 URL 都被丢弃，回答末尾的来源列表是模型自己写进正文的 Markdown，已实测出现复述与实际不一致。是否持久化与展示尚未决定（个人资料库已决定回答不展示来源）。
- 记忆不做版本管理，每轮记忆判断也不在对话中提示：误改后只能由用户说明要恢复的内容，或在记忆页面重新编辑（`memory-spec.md` §3.3）。
- 资料目录每轮都要纳入用户改动并解析全部资料的 frontmatter，资料很多时有额外开销；说明由模型填写，写得不好时 Agent 可能想不到去读对应资料。
- 用户改动不是实时监听：直接改文件后，要等下一次资料库操作才纳入版本；每次操作都会先做一次 `git status`，资料库很大时有额外开销。删除、移动与恢复前需取得用户同意由工具说明约束模型遵守，程序只保证这三个工具只在用户对话轮可见。
- 历史检索在第一次搜索时才把已有历史写进索引，历史很多时这次搜索会明显变慢；进行中的轮次搜不到。日期过滤按本机时区换算，服务与用户不在同一时区时自然日边界会有偏差。
- 资料编辑页的“未保存离开”只拦截页面内的返回按钮与浏览器关闭或刷新；通过侧栏或底部 tab 跳走时不提示（当前路由不支持导航拦截）。
- 归档由模型自主判断，可能漏归档或在同一任务里重复归档；真实模型验收覆盖了“确认发送后归档一次”的主路径。
- Skills 基础段与轨迹段已完成；后台复盘（阶段 3）、使用统计与陈旧标记（阶段 4）尚未实现，因此 `skill_changes` 里的 `proposed` 目前没有生产者（只有 `review_job_id` 列与审批界面就绪，D 阶段接入后前端零改动），`record_skill_view` 与 `GET/PUT /api/skills/settings` 也还没有。
- 执行轨迹随实现明确三点：参数值与返回内容只存本地 SQLite（契约 §3 已按用户确认改为参数含值）；轨迹条目写入失败只告警、不失败工具调用本身，该条调用可能缺席轨迹；一次性会话（记忆判断、记忆回顾）不记轨迹，D 阶段复盘会话的工具调用按 ReviewJob 记录、不进任务轨迹。中断重试保留已发生的工具条目，只替换半截回答。
- 轮首的上下文占用只在复用已有 SDK 会话的轮次读取（压缩检查顺带记录）；任务首轮没有先前会话可读，「轮开始」显示“未记录”，属既定行为而非数据缺失。
- 内置工具回调只记录功能接入后的新调用，不自动回填历史任务。此前用于验证缺口的任务 `8ca57878-70ca-46c7-97dd-8995f712eef9` 已按该轮 SDK 会话中逐次配对的调用与结果补回 2 条 WebSearch、2 条 WebFetch；其他历史任务若缺内置工具条目仍保持原状。
- 轨迹工具行写入后即通过任务 SSE 提醒页面重读；独立临时实例的真实只读任务在轮次仍为 `running` 时依次看见 WebSearch、WebFetch 的 `running → ok` 四次通知。工具分隔同一轮助手文字时仅在本轮最后一段保留一个“复制回答”，复制内容覆盖该轮全部助手文字。
- 执行中终止随实现明确四点。第一，终止只作用于这一轮：模型调用停下、已流出的文字与工具记录保留，这一轮记为 `interrupted`，任务本身、其他轮次与待确认草稿都不受影响；按用户要求时间线不补程序提示，页面靠这一轮的徽标与可重试入口说明结果。第二，终止的落库口径与进程中断一致，因此没有产生操作记录的轮次同样能用既有重试入口在原位置重试；已经确认并执行的外部写不会被撤销，也不会回滚。第三，会话句柄在该轮建立 SDK 客户端时登记，所以「有进行中的调用」不等于「一定拿得到句柄」：拿不到时改为取消该轮的协程，取消发生在协程取得运行权之前只落库记中断、由协程读到状态后自行退出。第四，任务页在服务端这一轮进行中把右下角按钮换成终止，这一轮里不再发送新消息（此前能在执行中追发并排队），已写的内容与附件留在输入框，终止或结束后再发。
- 任务页把“过程”与“结果”分开呈现：折叠分组里的思考叙述按过程样式（`--text-sm`、次要色、与工具行同一档行距），正式回答仍是 `--text-md` 正文色；运行中的轮次不折叠，叙述同样按过程样式与紧随其后的工具行连成一段。判定依据仍是“本段最后一次工具调用之前的助手文字”，所以模型若把结论写在最后一次工具调用之前，那段文字会落进过程区并按过程样式显示（`observability-spec.md` §2）。该呈现用真实任务页核对：过程叙述 13px／次要色，与前后工具行行距 8px，正式回答 14px／正文色。
- 任务页工具行已为当前技能、日历、历史、邮件、资料及本轮开放的 SDK 内置工具提供中文动作与对象；完整原始工具名、参数、返回和调用 ID 保留在展开区，未知工具沿用原名。日程创建显示“尝试创建”，不把成功返回误写为已创建。
- 技能的不一致检测按 Git 工作区判定：直接改磁盘（未提交）的技能退出目录、装配与 `skill_view`，管理页仍可打开并在保存后恢复；用户自行 `git commit` 的改动没有变更留档，运行时与“服务写入”无法区分，维护阶段补审计。
- 手动选择的正文上限（10 个、40000 字符）在提交校验与装配两处执行；装配时超出的条目跳过并记日志，不失败整轮。
- `skill_manage` 对 `managed=false` 技能的直接写入只由“仅用户发起的对话轮可见”保证；后台会话当前结构上拿不到该工具，D 阶段给复盘会话加技能工具时需要显式确认这条约束。
- 可观测性随真实验收记录五点口径与偏差。第一，请求级条目仍只取 `AssistantMessage.usage`（契约 §3），实测本地 CN CLI 1.1.38 在这一层把 `input_tokens`／`output_tokens` 填成 0、`credits` 缺省、`request_id` 为空，只有 `message_id` 可用，执行详情的逐请求行如实显示 0／“未记录”。去重键退化为 `message_id`：同一 `message_id` 的多条消息按一次请求计（SDK 会把一次请求的多个内容块分条上报），拿不到 `request_id` 时无法再校验是否重名。为补上真实数字（经用户确认改契约），sdk_result 另存 `ResultMessage.usage` 的末次请求读数 `result_usage` 与轮末会话累计快照 `session_totals`（model_usage 汇总 token、total_credits），读取面以相邻轮快照差值推算本轮消耗并标注「按相邻轮累计差值推算」：任务首轮快照即本轮消耗，前一轮缺快照（如中断轮）、差值回落（会话被重置）或快照全零时不推算，该轮退回请求级求和或“未记录”；历史旧轮次无快照，维持“未记录”不回填。复验（`tests/acceptance/qoder_observations.py`）确认此运行时把数字层全部置零：`result_usage` 的 token 为 0（`request_id` 与上下文比例为真）、`session_totals` 全 0，另探得 `get_usage_info()` 的 session 层同样为 0；账号配额层（userQuota／addOnQuota）有真实数字，但属账号级累计、粒度粗，不进轮观测。因此本机当前逐请求行、末次请求行（只在有正数时显示）与合计都如实显示“未记录”，推算机制待运行时上报真实读数后自动生效，全零快照不会被显示成“本轮消耗 0”。第二，实测真实的权限拒绝先到 PreToolUse、后到权限回调，因此 `observation_steps.started_at` 可能有值，`_begin` 的注释只覆盖“回调先到”的一半；两种形状在界面上都显示“已拒绝”，读取面不做区分。第三，压缩步骤的“后占用”是读取时刻的实测值而不是压缩效果的断言：`autoCompact` 关闭时网关在 `/compact` 完成后立刻读，实测这一刻 CLI 仍报 100%（窗口占用要到下一轮请求才按压缩后的上下文重算），同一个任务在下一轮的轮首读数才落到 3.6%；自动压缩没有前后实测，后占用取轮末读数回填。步骤行因此直接显示“占用 前% → 后%”，不声称回落幅度。第四，`sdk_result` 只存 `duration_ms`、`duration_api_ms`、`num_turns`、`is_error`、结束原因与逐请求用量；`ResultMessage.total_credits`、`model_usage` 是会话累计值，不落库。第五，观测只在任务轮次里产生：一次性会话（记忆判断、记忆回顾、标题与看图）与 `run_id` 为空的轮次不写观测，`num_turns` 存下来但不冒充“模型调用次数”（后者是去重后实际收到的 usage 条目数）。第六，任务页界面按用户决定两轮收窄（2026-09-26）：先去掉用量明细与步骤清单、只留材料／时长／上下文与一行异常概览，随后按用户要求删掉整张「执行详情」卡片，改为折叠组头只显示总时长、上下文移到输入框发送按钮左侧的标记与其面板（类别分解用运行时 `categories` 的百分比，不折算 token）。采集、`run_observations`／`observation_steps` 表、`usage_totals` 推算逻辑与 `GET /api/tasks/{id}/observations` 的返回都照旧保留并新增 `context_*.categories`；材料明细、异常概览与用量因此都没有界面呈现点，恢复其中任何一项都要先改规格 §2 与契约 §3–4。第七，上下文标记与面板只报最近一轮结束时的窗口占用比例和类别占比：读数不是实时值（正在跑的一轮与还没发送的内容不在里面），面板也不展示读数时间点与口径说明，需要判断时效时以折叠组头的时长为参照。第八，dict 材料的字符数口径已修正：`len(dict)` 数的是键的个数（“技能目录 2 字”其实是 2 个键），现在统一取渲染后文本的长度（`context.render_material`，含标题行），与模型实际收到的内容一致；历史轮次不回填。面板的类别分解要靠新写入的 `categories` 才有内容，旧轮次只显示占用比例。
