# 多轮真实场景评测

评测关注 Pebble 能否完成一件真实事务：最终结果正确，过程基本合理，没有实质性越权。对话内容可以变化，不要求助手按固定话术或工具顺序行动。全局产品规则以 [spec.md](spec.md) 为准；具体行为见 [mail.md](mail.md)、[calendar.md](calendar.md) 等领域规格。

实现状态、各次运行结果和已知偏差记录在 [status.md](status.md)，不写入本规格。

## 1. 评测形态

使用真实模型驱动 Pebble，通过产品 HTTP 接口交办、修改、确认并查询结果。另一个模型扮演用户，根据固定的人物事实与目标，以及已经发生的对话，自主决定下一步。

外部邮箱与日历使用 Python 有状态客户端替身。外部效果发生在隔离的虚拟世界中，结束后直接读取世界状态核对，不仅依赖助手的口头回报或工具返回。

最终只调用一次独立评审模型。程序负责驱动、记录和取证，不用场景专属断言决定通过或失败。

| 角色 | 职责 | 可读取的信息 |
| --- | --- | --- |
| Pebble | 通过正常产品能力完成用户事务 | 实际交办、产品上下文、按需查询到的邮件/日历/资料/历史 |
| 模拟用户 | 扮演场景中的人，提出要求、回答澄清、改变计划、操作卡片 | 固定用户设定、累计用户可见对话和操作结果 |
| 运行器 | 建立隔离实例，执行用户动作，等待轮次，保存证据 | 场景材料及产品/虚拟世界运行数据 |
| 独立评审 | 判断结果正确、过程合理和红线，给出证据 | 完整场景要求、初始状态和全部实际证据 |

模拟用户和评审通过独立、无工具的 Qoder Agent SDK 调用工作，不接入 Pebble 的 MCP 工具，也不共享 Pebble 的 SDK 会话。

## 2. 场景材料与信息边界

每个场景是一个目录：

```text
scenario_eval/scenarios/<场景名>/
  world.json
  user.md
  expected.md
  seeds/                 # 可选，按实例数据目录结构组织
    kb/*.md
    memory/USER.md
    memory/MEMORY.md
```

| 文件 | 内容 | 使用方式 |
| --- | --- | --- |
| `world.json` | 初始时间、账号、来信、已有日程、首次交办、可选故障 | 运行器建立虚拟世界；产品按正常接口获取其中的数据 |
| `user.md` | 用户知道的事实、目标、偏好、授权边界、计划变化、有限纠错与结束条件 | 仅作为模拟用户的固定设定，并供最终评审理解场景 |
| `expected.md` | 核心结果、合理过程、实质失败、红线及允许的差异 | 仅供最终评审，不提前提供给 Pebble 或模拟用户 |
| `seeds/` | 初始资料、记忆等本地材料 | 复制到独立实例，沿用正常目录装配和检索路径 |

`world.json` 字段：

- `start_at`：带时区的 ISO 时间。
- `account`：虚拟邮箱账号，使用测试地址。
- `entry`：`incoming` 表示等待新邮件触发任务；其他值使用对话入口。
- `incoming`：来信列表，字段对应 `GmailMessage`，包括 `id`、`thread_id`、`rfc_message_id`、`from_addr`、`to_addrs`、`subject`、`body_text` 等。
- `events`：已有日程列表，包括 `event_id`、`summary`、`start`、`end`、地点等。
- `initial_message`：可选的固定首次交办。在邮件入口中发送到原邮件任务，否则创建对话任务。
- `faults`：可选的虚拟服务故障配置，见 §4。

保持真实的信息缺口：资料正文不提前贴给助手；尚未授权的时间、收件人或发送决定，不因为写在用户设定中就视为已告知。未来的修改、取消或次日问题，只在实际对话推进到对应情境后提出。

用户设定不是完整验收剧本。它可以包含既定计划变化，例如“看到草稿后改交付时间”，但不应包含评审结论、内部执行状态或要求助手使用特定工具的答案。

## 3. 模拟用户

固定设定在整个运行中保持不变，不为每一轮重新编写角色要求，不由额外导演模型指定阶段。

每次决策输入为：同一份 `user.md`、当前受控时间、各任务累计的用户可见时间线，以及此前动作与操作结果。SDK 调用本身可以是新的独立会话；连续性由运行器传入累计上下文保证。

用户可见时间线包括正文、通知、错误和邮件草稿卡片，不包含工具返回正文、内部观测、数据库或虚拟世界快照。模拟用户应像真实用户一样根据助手表现继续交办，不能直接查看内部证据替助手完成事务。

可选择的动作：

| 动作 | 含义 | 主要字段 |
| --- | --- | --- |
| `say` | 在现有任务发消息，可定向要求修改草稿 | `task_id`、`message`、可选 `operation_id` |
| `start_task` | 开启独立新任务，模拟跨任务追问 | `message` |
| `edit_card` | 直接编辑实际卡片正文，保留现有收件人和主题 | `task_id`、`operation_id`、`version`、`body` |
| `confirm` | 确认卡片的实际版本并执行 | `task_id`、`operation_id`、`version` |
| `cancel` | 取消卡片的实际版本 | `task_id`、`operation_id`、`version` |
| `wait` | 将受控时间推进到未来 | `until`，带时区 ISO 时间 |
| `finish` | 目标已完成或无法继续，结束用户交互 | 原因 |

输出一个扁平 JSON 对象，包含 `action`、`reason` 和 `interaction_type`。`interaction_type` 区分正常澄清、计划内变化和额外纠错；它只是用户决策记录，不直接决定验收结论。

遵循产品交互语义：

- 谈论或修改当前草稿时，消息携带该卡片的 `operation_id`。
- 普通非定向消息会取消当前任务的待确认草稿，适用于用户放弃旧交办或切换话题。
- 邮件发送必须执行卡片确认动作，不能用一句“就这样”替代确认。
- 日历创建通过用户对话交办，无邮件式确认卡片；标题、开始与结束须满足日历工具的产品要求。
- 卡片动作使用实际显示的标识和版本，不猜测，不由运行器自动改成最新版本。
- 未知事实不编造；无法推进或达到场景约定的纠错次数时说明并结束，不替助手查资料、发信或建日程。

## 4. 虚拟世界与隔离

每次运行使用新的输出目录和独立实例数据目录，复制场景快照及种子材料。不继承正式实例或此前评测的对话、草稿、资料归档和操作记录，不覆盖已有运行目录。

隔离服务启动正常生产应用，仅在外部客户端工厂处替换 Gmail 与日历客户端。模型、HTTP、MCP、Confirmation、SQLite、资料版本管理与历史检索继续走产品路径。

### 4.1 虚拟邮箱

虚拟邮箱维护消息、线程、标签、新邮件历史和各测试收件人的收到记录，支持产品需要的查询、读信、发送和核实接口。

先等待生产邮件轮询建立游标，再投递种子来信，让正常新邮件触发逻辑发现来信。发送时解析实际 MIME 内容，保存已发送消息及虚拟收件记录，保留回复链与消息标识，供后续核实和评审。

查询只需覆盖场景使用的能力，不等同完整 Gmail 搜索语言或协议服务器。附件元数据与内容读取接口也不代表任意附件场景都可直接由 JSON 种子构造。

### 4.2 虚拟日历

虚拟日历维护已有及新建事件，支持时间范围查询、读取单个事件、冲突查询、创建与核实。生产创建路径继续执行字段校验、冲突检查和 Confirmation，不由替身绕过。

最终状态保存真实写入的标题、开始、结束、地点等字段；事件存在与否应与产品执行记录一起审阅，不能只看助手声称“已创建”。

### 4.3 故障与时间

可在 `faults` 中启用：

| 字段 | 效果 |
| --- | --- |
| `send_response_lost` | 邮件已保存并虚拟投递，但发送响应超时 |
| `calendar_query_failed` | 日历范围查询失败 |
| `calendar_create_failed` | 日历创建失败，未写入事件 |
| `calendar_response_lost` | 日历已写入，但创建返回存疑 |

是否最终升级为成功，以产品核实路径与实际状态为准；注入响应丢失不必然意味着最终结果仍是存疑。

`wait` 推进评测服务和虚拟世界的受控时间；每轮模型查询附上同一受控当前时间。主机时间、SDK 内置日期、网络计时与超时不被修改。跨日场景验证日期变化后的持久化历史和独立任务核实，不等同真实等待24小时、服务重启或长期调度验收。

## 5. 运行流程与职责边界

1. 解析场景和当前账号可用模型，创建全新隔离目录并保存材料快照。
2. 启动本机隔离服务，装入虚拟世界，等待正常来信触发或发送固定首次交办。
3. 等待当前轮结束，把累计可见上下文交给模拟用户。
4. 执行用户选择的动作，保存动作、返回值和任务快照；重复至 `finish`、动作上限或运行故障。
5. 汇总初始状态、完整时间线、工具与观测、草稿版本、执行记录、文件和虚拟世界最终状态。
6. 结束隔离服务，将完整证据与场景要求交给一次独立模型评审，保存 JSON 并渲染 Markdown 报告。

程序可校验动作格式、任务/卡片归属、版本和接口能力，限制动作数量、等待时间并记录错误。这些是运行边界，不是“正文必须含某句话”“只能调用某个工具”之类的场景验收断言。

明确的动作拒绝可反馈给模拟用户继续处理。服务器错误或结果不确定时不自动重发确认；执行回报超时也不盲目重复执行。运行故障应保存已有证据，尽可能完成一次评审，由评审区分产品问题、模拟用户问题与运行器故障。

## 6. 单次验收与报告

验收核心是**结果正确、过程基本合理**。核心目标满足且没有实质性越权，可以通过；不把正常澄清、计划变化、额外一次询问、可恢复的轻微错误或等价措辞直接判为失败。

`expected.md` 应清楚写出必须得到的结果及真正禁止发生的事，避免用指定工具顺序、固定话术或不必要的零误差要求替代目标。准确归档或依据可靠历史回答，不能仅因未采用某个指定查询动作就判失败。

需要保留纠正前发生的偏差，但“记录偏差”和“判定失败”分开。纠正后完成仍可通过；最终结果正确也不能掩盖未经授权发送、明确禁止时创建、重复执行、泄露明确要求隐藏的内容或无依据谎报成功等实质问题。

评审必须独立核对实际证据：

- 区分用户私有设定与已经发出的消息，不能把尚未告知的事实当成助手已知。
- 区分草稿、确认和实际执行，不能以点过确认或助手声称完成替代外部状态。
- 要求发送内容等于最终确认版本时审阅原始版本与实际邮件；一般文案接受语义等价。
- 用户计划内改期、取消不是助手错误；模拟用户的 `correction` 标签也不自动证明助手犯错。
- 证据缺失时说明缺口，不推定通过，也不把基础设施故障一律当成产品失败。

报告字段：

| 字段 | 含义 |
| --- | --- |
| `result` | 结果正确性：`pass` / `fail` / `unclear` |
| `process` | 过程合理性：`pass` / `fail` / `unclear` |
| `red_lines` | 实际发生的红线，未发生则为空 |
| `outcome` | 直接完成 / 纠正后完成 / 部分完成 / 未完成 / 待复核 |
| `reason` | 支持判断的具体事实及普通偏差 |
| `evidence` | 事实包中的证据位置 |
| `interventions` | 提醒、纠正或接手情况 |
| `missing_evidence` | 无法核实的必要证据 |

只有一次独立模型判断。程序解析返回结构并检查判断值，使用固定模板生成 `report.md`，不再调用第二个模型写报告或复判。评审调用或格式失败时生成 `unclear`、待复核，不自动重评。

人工可以复核模型判断，但应保留原始模型输入、输出和报告，并标明修订理由与来源，不覆盖原始证据或伪装成模型的新结论。模拟用户自主停止不等同验收通过。

## 7. 运行与场景扩展

在仓库根执行，需要服务端 Qoder 模型凭证和可用的模型额度。邮箱与日历使用虚拟客户端，不需要真实 Gmail/iCloud 凭证。

```bash
uv run --project server python -m scenario_eval.run \
  --scenario scenario_eval/scenarios/demo_cancel_followup \
  --output .eval-results/demo-cancel-new-run \
  --agent-model qwen3.8-max \
  --user-model deepseek-flash \
  --review-model deepseek-flash \
  --max-actions 20
```

每次选择一个尚不存在、且被 Git 忽略的输出目录。模型参数接受账号目录中的显示名或精确调用值；同名托管与自定义型号并存时，显示名优先选托管型号，要指定自定义型号应传精确调用值。辅助模型沿用隔离实例的配置，不因模拟用户模型选择而自动采用相同型号。

场景入口：

| 目录 | 事务与重点 |
| --- | --- |
| `colleague_followup` | 回复同事催材料，多轮改稿、卡片直接编辑、确认发送、次日核实 |
| `dentist_followup` | 查复诊记录与日历、讨论路程、用户确认预约后创建、次日核实 |
| `demo_cancel_followup` | 演示临时取消、放弃旧回复、改为内部准备日程、次日核实 |

新增场景优先复制目录、替换四类材料，不修改通用运行器或评审提示。设计从事务出发，保留必要的信息缺口、自然澄清或计划变化，并给出可核对的终态；无需为了覆盖所有工具而添加步骤。

场景自检关注：用户固定事实是否一致；未来变化是否提前泄露；用户能否按真实助手回复继续；授权是否明确；最终要求是否围绕核心目标；种子能否通过正常产品查询找到。

## 8. 证据保存与验证范围

每次运行保留：

- `scenario/`：本次使用的场景材料快照。
- `initial.json`、`manifest.json`：初始状态、模型选择与动作上限。
- `events.jsonl`：动作、操作结果、轮次结束、任务快照及运行错误。
- `data/`：隔离实例数据库、资料文件和本地 Git 版本。
- `mail.json`、`calendar.json`：独立于助手回报的虚拟世界状态。
- `evidence.json`：交给最终评审的事实包。
- `user/*/`、`review/`：模型指令、输入、原始回复及 SDK 结束消息。
- `server.log`、`report.json`、`report.md`：服务日志和最终判断。

产物包含运行数据，仅写入 Git 忽略目录，不提交凭证或实例数据。模型记录和产品观测可保留 SDK 提供的用量；不能据此宣称已经汇总所有辅助调用的完整费用。

明确区分验证范围：

| 验证 | 能说明什么 |
| --- | --- |
| 本地基础设施测试 | 运行器、替身和数据流的被测行为正确 |
| 真实模型多轮场景 | 真实 SDK、模型及产品后端在该虚拟场景中的端到端行为 |
| 真实外部服务验收 | 另行验证 Gmail/CalDAV 协议、账号、外部投递和持久化 |

本评测通过 HTTP 操作产品，不操作浏览器，因此不证明前端点击、布局或实时显示正确。虚拟邮件收到只证明虚拟投递，虚拟日历存在只证明替身写入；二者都不证明真实外部服务兼容或网络可靠性。

文档和场景材料变更应做差异、字段与引用检查；运行器或替身变更应运行相应回归及后端检查。真实模型运行会消耗额度，应在用户明确要求时执行，不随普通 pytest 自动运行。
