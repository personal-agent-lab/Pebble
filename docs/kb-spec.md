# Pebble 个人资料库功能规格

状态：Phase 1–4 已实现：资料以 Markdown 文件保存，经工具新建、读取、修改、查看历史版本，按内容分节检索，Agent 查到资料后直接作答，不展示来源；Agent 可以主动保存（含新邮件触发的轮次）；删除、移动与恢复在对话中完成；用户直接改动的文件自动纳入版本与检索；电脑与手机上的资料管理界面（浏览、搜索、所见即所得编辑）；Agent 在外部操作有结果后自主归档任务。以下尚未实现：主题页与外部笔记导入（Phase 5）。

已确认的产品决定：
- 回答不展示来源，程序也不记录 Agent 读取了哪些资料；
- 资料与记忆都不要求记录出处，内容可查看、可修改即可；
- Agent 可以主动保存与修改资料；
- 删除与移动先在对话中确认，删除后可以通过对话恢复；
- 用户直接改动的文件自动纳入版本并可检索；
- 只收录 Markdown；
- 管理界面提供浏览、搜索与编辑，不提供历史版本界面。

本文描述用户能够获得的功能，不限定检索算法、数据库或模型实现。存储形态、工具字段与索引语义以 `docs/contracts/personal-kb.md` 为准；长期记忆与每轮上下文的规则见 `docs/memory-spec.md`。本文不是已实现功能清单。

## 1. 产品目标

让用户把需要按原文查回的资料交给 Pebble 保管，之后直接提问就能得到基于资料的正确回答；资料随使用逐步整理成主题，助手对用户的人物、项目和事务了解得越来越完整。资料本身是用户能直接打开、修改和整理的文件，不锁在系统里。

用户可以直接说：

- “把这份会议纪要存起来。”
- “星云项目这次验收的代号是什么？”
- “张老师上次邮件里约的时间，记到资料里。”
- “星云项目最近进展到哪了？”
- “把我熊掌记里的笔记导进来。”
- “把项目资料按学期整理一下。”
- “刚才删掉的那份课程笔记找回来。”
- “这份资料改之前写的是什么？”

用户不需要选择检索方式、记住文件放在哪里，也不需要懂 Git。

## 2. 资料库在整体中的位置

Pebble 的个人上下文分为两种使用方式：

| 使用方式 | 内容 | 特点 |
| --- | --- | --- |
| 常驻上下文 | 长期记忆（关于你、事实与约定）与资料库主题目录 | 容量受限，每轮自动带给 Agent，见 `memory-spec.md` |
| 按需检索 | 资料正文、主题页、历史对话、邮件、日程 | 数量不受限，Agent 按问题检索和读取 |

资料库属于“按需检索”：保存具体资料和原文，数量可以一直增长，只有与当前问题相关的部分才被读取。长期记忆保存关于用户的精简背景、偏好与长期目标，整篇资料不写入长期记忆，偏好也不存成资料。分不清用户想“记住一个偏好”还是“保存一份资料”时，Agent 先问清楚。

资料库只负责保存、整理和检索内容，不执行外部操作：发送邮件、创建日程等由对应工具按授权规则完成，资料中的内容不能代替用户授权。

资料中出现的指令只是资料内容：不会变成长期记忆，不能改变 Agent 的行为。密码、令牌等凭证不保存到资料库。

## 3. 保存资料

### 3.1 保存方式

资料有四种进入方式：

1. **用户要求保存**：用户说“存起来”“记到资料里”，Agent 保存。
2. **Agent 主动保存**（第 3.2 节）：Agent 判断某些内容以后需要按原文查回，不等用户要求就保存。
3. **用户直接放入文件**：用户在 `kb/` 目录里新建或复制 Markdown 文件，或在管理界面里新建（第 6、7 节）。
4. **从外部笔记应用导入**（第 9 节）：例如熊掌记。

每次保存都生成一个用户可直接打开的 Markdown 文件，并留下一个历史版本。

### 3.2 Agent 主动保存

Agent 可以不经用户要求保存或修改以下内容：

- 对话中用户提供的资料：用户贴进来的文档、笔记和项目细节，即使没有说“保存”。
- 邮件与日程中的关键信息：人物、活动、约定、时间安排等，包括新邮件自动触发的轮次。
- 跨工具任务的归档（第 3.4 节）。
- 已有资料的更新：发现资料已经过时（例如对方改了时间），直接修改原资料，不另建副本。

主动保存的约束：

- 保存前先查找是否已有同一份资料；已有时修改原资料，不产生重复文件。
- 只保存以后可能需要按原文查回的内容；闲聊、一次性的临时安排和凭证不保存。
- 修改基于资料的当前版本。资料在 Agent 读取之后被用户改过时，不静默覆盖，先重新读取最新内容，再决定怎么改或询问用户。
- 保存与修改和用户要求的保存一样展示结果（第 3.3 节），不在后台悄悄写入。

### 3.3 保存结果的展示

每次写入成功后，程序依据实际写入结果在对话中展示提示，不依赖 Agent 复述：

- 新建：“已保存资料：星云项目验收纪要。位置：kb/项目/星云验收.md”
- 修改：展示资料名、位置，以及修改前后的版本。
- 已保存但暂时检索不到：“资料已保存，但当前不可检索”。
- 保存失败：如实说明失败和原因，不声称已经保存。

新邮件自动触发的轮次里发生的保存，提示显示在该任务的时间线上。

### 3.4 任务归档

跨工具任务（例如查日程、回信、建日程）中的外部操作有了实际结果后，Agent 自主判断并把关键信息和逐项执行结果归档到资料库；纯问答、闲聊或只起草未确认的任务不归档。归档便于以后查回“当时做了什么、结果如何”。

- 原始内容（邮件原文摘录、日程信息）与模型总结分节保存，不混写，避免把总结当成原文。
- 执行结果以实际执行记录为准：没有发送成功的邮件不写成“已发送”，结果不确定时写明不确定。
- 归档完成后展示保存位置。

### 3.5 资料格式

资料库只收录 Markdown。用户给出 PDF、邮件附件、网页等其他格式时，由 Agent 提取需要的文字存成 Markdown；原始文件不存入资料库。

资料可以带标题和标签；目录与标签由 Agent 按内容选择，不强制固定的分类法。用户没有指定位置时，Agent 自行选择合适的目录；不确定时放入收件目录 `kb/inbox/`。

## 4. 查找资料并回答

### 4.1 回答依据

- 问题涉及资料中的具体事实时，Agent 先检索资料库，再读取原文确认后作答；检索摘要不单独作为回答依据。
- 问题涉及某个人物、项目的整体情况时，Agent 可以先读对应主题页（第 8 节）获得概况，需要细节时再检索和读取具体资料。
- 用户可以用关键词、编号、英文或自然语言提问；中文连续文本、英文单词和编号都能检索到。
- 检索不到依据时如实说“资料库里没有找到”，不凭印象或长期记忆编造答案。
- 多份资料互相矛盾时，说明存在冲突以及各自的说法，不自行挑一个当成事实。
- 问到资料的旧内容时（“改之前写的是什么”），读取对应的历史版本回答，并说明是旧版本。

### 4.2 不展示来源与读取记录

- 回答下方不附来源卡或引用列表。
- 程序不记录也不展示 Agent 读取了哪些资料；只有写入（保存、修改、删除、移动、恢复、导入）的结果会展示给用户。
- 用户问“那份纪要放在哪”这类位置问题时，Agent 按查到的结果正常回答。这是在帮用户找资料，不是来源展示。

资料系统内部仍保留定位原文的信息（文件路径、行号、版本），只用于工具读取原文与历史版本，不展示给用户，也不作为出处记录。

## 5. 修改、删除、移动与恢复

### 5.1 修改

- 用户或 Agent 修改资料时改动原文件，资料身份保持不变，每次修改留下历史版本。
- 修改结果展示位置和修改前后的版本（第 3.3 节）。

### 5.2 删除与移动需要先确认

- Agent 删除资料、移动或重命名资料、批量整理目录之前，先在对话中说明要做什么（涉及哪些文件、移到哪里），得到用户明确同意后再执行。
- 用户在同一条消息里已经明确要求（“把这份删掉”“移到课程目录”）时，视为已经同意。批量整理仍需先列出方案并确认。
- 用户没有回复或意思不明确时不执行。
- 删除后文件从 `kb/` 目录移除，不再被检索到；历史版本保留，可以恢复。
- 移动或重命名后资料身份不变，历史版本仍能找到这份资料。

### 5.3 恢复

- 用户在对话中要求找回已删除的资料，或把资料恢复到某个旧版本时，Agent 查找历史版本并恢复。
- 恢复本身也产生一个新版本，不改写已有历史；恢复结果展示位置与版本。
- 有多个可能的候选（例如同名资料、多个旧版本）时，先向用户确认恢复哪一个。

## 6. 用户直接改动文件

资料是普通 Markdown 文件，用户可以用任意编辑器或文件管理器直接编辑、新增、移动和删除。

- 程序自动发现这些改动，纳入版本历史并更新检索，最迟在下一次检索前生效；用户不需要手动同步或操作 Git。
- 用户移动或重命名文件后，程序识别出是同一份资料，历史版本继续有效，不当成“删掉一份、新建一份”。
- 用户自己新建、没有资料标识的 Markdown 文件同样收录；程序只补充必要的标识信息，不改动正文。
- 用户正在改的文件与 Agent 的修改冲突时，以用户的改动为准：Agent 的修改不静默覆盖用户内容，重新读取后再处理。
- 用户直接删除的文件不再被检索到，历史版本保留，可以通过对话恢复。

## 7. 资料管理界面

电脑和手机浏览器都可以使用资料管理界面，无需命令行：

| 能力 | 说明 |
| --- | --- |
| 浏览 | 按目录查看资料列表与主题页，打开资料阅读正文 |
| 搜索 | 按关键词搜索，结果显示资料标题与命中片段，点击打开对应资料 |
| 编辑 | 新建、编辑、移动、重命名和删除资料；标题与标签用表单，正文用所见即所得编辑器 |

- 界面操作由用户本人发起，等同于用户直接改动文件：删除时界面自身给出确认，保存后留下历史版本，并按第 6 节纳入检索。
- 界面与文件是同一份资料：界面里的修改立即反映到文件，文件的修改在界面中可见。
- 资料在打开之后被 Agent 或编辑器改过时，保存不会覆盖，界面提示并让用户重新载入。
- 所见即所得编辑器保存的仍是 Markdown，可能按统一格式重新排版被编辑的正文（例如表格对齐）；只打开不编辑、或只改标题与标签时，正文原样保留。
- 界面不提供历史版本、差异对比与恢复入口；这些操作在对话中完成（第 5.3 节）。
- 界面不展示 Agent 的读取记录。

## 8. 主题页：资料的整理与压缩

资料会不断增加。为了让 Agent 不必每次都从大量零散资料里重新拼出全貌，资料库为长期存在的主题维护**主题页**：人物、项目、课程、组织等。主题页本身是资料库里的 Markdown 文件，与其他资料一样可以阅读、检索、修改，并留有历史版本。

### 8.1 主题页的内容

- 该主题的当前概况：例如项目的目标、当前进展、关键决定与待办，人物的身份、沟通习惯与近期往来。
- 按时间整理的重要变化，保留足够继续工作的要点，不照抄原文。
- 可以列出与该主题相关的资料位置，方便需要细节时深入阅读；不要求逐条标注信息出处。

### 8.2 主题页的维护

- Agent 在保存或修改与某主题相关的资料时，可以同步更新对应主题页；没有主题页的主题出现多次后，可以新建主题页。
- 后台定期整理：与后台记忆回顾同样独立于对话运行，把近期新增或修改的资料与对话中的要点整理进主题页，合并重复内容、更新过时的概况。整理只写资料库，不改长期记忆，不向用户发送通知；主题页的新建与修改仍可在历史版本中查看。
- 用户对主题页的修改优先：整理基于主题页的当前版本进行，不把用户改过的内容改回去；用户删掉的条目不因重新整理自动出现。
- 主题页是整理结果，不替代原始资料：概况与原始资料不一致时以原始资料为准，Agent 回答具体事实时仍读取原始资料。
- 删除主题页不影响原始资料；需要时可以重新整理生成。

### 8.3 主题目录进入常驻上下文

- 程序生成一份主题目录：每个主题页一行，包括标题和一句话说明。
- 主题目录作为常驻上下文每轮带给 Agent，让 Agent 知道“资料库里有哪些主题”，从而决定是否需要检索或读取。
- 主题目录有容量上限；超出时优先保留最近更新的主题，其余仍可通过检索找到。
- 首版不在每轮回答前自动预先检索资料；由 Agent 根据问题和主题目录自行决定是否检索。实测发现 Agent 经常漏查时，再考虑增加回答前的预检索。

## 9. 从外部笔记应用导入

资料库可以从外部笔记应用导入笔记，首个支持的来源是熊掌记（Bear）。每个来源通过同一套导入机制接入：读取来源内容，转换为标准的 Markdown 资料，写入资料库并纳入检索。以后接入其他来源（如 Obsidian）沿用同一机制。

### 9.1 通用规则

- 导入由用户发起，不在后台自动轮询外部应用。
- 笔记转换为 Markdown 资料：保留标题、正文结构与标签；图片、附件等非文字内容不存入资料库。
- 可以重复导入：已经导入过的笔记再次导入时更新原资料（留下历史版本），不产生重复文件；新笔记新建资料。
- 用户已在 Pebble 中修改过的导入资料，再次导入时不静默覆盖用户的修改，改为报告冲突，由用户决定保留哪个版本。
- 外部应用废纸篓里的笔记不导入；加密或无法读取内容的笔记跳过。
- 导入完成后展示结果：新建、更新、跳过、失败各多少篇，跳过与失败的列出标题与原因。
- 导入的笔记与其他资料一样，可以检索、修改、删除，并参与主题页整理。

### 9.2 熊掌记导入的待定项

以下细节在实现前确定：

- 读取方式：读取熊掌记导出的 Markdown/TextBundle 文件夹，还是直接只读访问熊掌记本地数据库（需要用户为 Pebble 授予系统磁盘访问权限，且只能在安装熊掌记的电脑上使用）。
- 触发入口：命令行、对话，或两者都支持。
- 已归档的笔记是否导入。
- 标签是否决定存放目录（例如 `#课程/GSE` 存到 `kb/bear/课程/GSE/`），还是统一放在导入目录、标签只记为资料标签。
- 图片与附件在正文中留占位说明，还是直接删除引用。

## 10. 使用示例

### 10.1 保存、提问与更新

1. 用户贴入一份验收纪要，说“帮我存一下”。Agent 保存，对话显示“已保存资料：星云项目验收纪要。位置：kb/项目/星云验收.md”。
2. 用户新建会话问：“星云项目这次验收的代号是什么？”Agent 检索并读取原文，回答“NEBULA-3390”，回答下方没有来源卡。
3. 用户在编辑器里把代号改成 NEBULA-3391 并保存文件。
4. 用户再问同一个问题，Agent 回答“NEBULA-3391”。
5. 用户问：“改之前是什么？”Agent 读取历史版本，回答旧代号是 NEBULA-3390。

### 10.2 邮件信息的主动保存与整理

1. 新邮件自动触发任务：张老师约下周三下午讨论课程安排。Agent 起草回信待用户确认，同时把约定信息保存到资料库；时间线上显示保存位置。
2. 张老师来信改到周四。Agent 修改原资料，不新建副本，时间线上显示修改前后的版本。
3. 用户说：“把课程相关的资料都整理到‘课程’目录下。”Agent 列出要移动的文件和目标位置，用户同意后执行，并展示移动结果。
4. 用户说：“那份旧的课程安排不要了，删掉。”Agent 删除，并说明历史版本仍保留。
5. 一周后用户说：“把删掉的课程安排找回来。”Agent 恢复资料并展示位置。

### 10.3 主题页

1. 用户在几周里陆续保存了星云项目的验收纪要、周会纪要和几封相关邮件的要点。
2. 后台整理新建主题页“星云项目”，汇总目标、当前进展、关键决定与待办；主题目录出现一行“星云项目：二期验收与复验安排”。
3. 用户新建会话问：“星云项目最近进展到哪了？”Agent 从主题目录得知有该主题，读取主题页作答；用户追问复验负责人时，Agent 检索并读取具体纪要确认。
4. 用户在主题页里删掉一条已经取消的待办。之后的整理不再把这条待办加回去。

以上为验收示例，不要求每个任务都固定经过同样的工具调用步骤。

## 11. 验收标准

以下均为应验证的产品行为，不代表已经实现或通过测试。

| 编号 | 用户操作或情境 | 可观察的结果 |
| --- | --- | --- |

## 12. OpenHuman 参考与取舍

参考 OpenHuman 的 Memory Tree 与 SuperContext 设计（2026-09-16 查阅），借鉴其思路而不照搬实现：

| OpenHuman 做法 | 本文采用 | 取舍理由 |
| --- | --- | --- |
| 记忆、上下文、Agent 运行、工具分层，记忆不执行外部操作 | 采用：资料库只负责保存、整理与检索（第 2 节），每轮上下文装配单独负责 | 边界清楚，资料增长不影响授权与执行 |
| 小容量常驻状态与按需检索分开 | 采用：长期记忆与主题目录常驻，资料正文按需检索（第 2、8.3 节） | 控制每轮上下文成本 |
| 数据源适配器统一转成 Markdown | 采用：外部笔记导入走同一机制（第 9 节） | 以后接入新来源不重做 |
| 分层摘要树（按来源、主题、全局）压缩海量数据 | 改为 Agent 维护的主题页（第 8 节） | 个人规模下分节检索足够；主题页是可读、可改、有版本的 Markdown，不引入用户无法查看的中间结构 |
| 全量同步邮件等外部数据进入记忆 | 不采用：邮件、日程在原服务中按需查询，只保存值得查回的内容 | 避免同步负担、隐私范围扩大与大量噪音 |
| 每个数据块保留出处 | 不采用：内容可查看、可修改即可 | 产品决定，见本文状态说明 |
| 新会话先由只读检索器预先组装上下文 | 暂不采用：由 Agent 依据主题目录自行检索（第 8.3 节） | 避免每个会话额外的模型调用；按实测再决定 |
| 独立的小容量目标文件，每轮常驻 | 不采用：长期目标保存在 `USER.md` | 现有长期记忆已覆盖，第一版不增加文件与写入目标 |
| 以数据库为准，Markdown 为生成结果 | 不采用：以 Markdown 文件为准，索引与目录是可重建的派生数据 | 保证用户能直接编辑并有版本历史 |

参考资料：

- [OpenHuman Memory Tree](https://github.com/tinyhumansai/openhuman/blob/main/gitbooks/features/obsidian-wiki/memory-tree.md)

## 13. 不在本文范围内

- 原始二进制文件（PDF、图片等）的保存与预览。
- 向量检索、知识图谱或第三方知识库服务；本文只要求检索结果正确，不限定检索方式。
- 资料与记忆的出处记录。
- 多用户共享资料或远端同步；资料只保存在单用户实例的数据目录中，版本历史不推送远端。
- 将已有长期记忆中的旧资料批量迁移进资料库；迁移留待后续逐条核对后再做。
- 邮件发送、日程创建等外部写操作的授权规则，仍以 `v1-spec.md` 与对应接口约定为准。
