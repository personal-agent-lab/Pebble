# Pebble 个人资料库功能规格

已确认的产品决定：
- 回答不展示来源，程序也不记录 Agent 读取了哪些资料；
- 资料与记忆都不要求记录出处，内容可查看、可修改即可；
- Agent 可以主动保存与修改资料；
- 删除与移动先在对话中确认，删除后可以通过对话恢复；
- 用户直接改动的文件自动纳入版本并可检索；
- 资料只收录 Markdown，正文可以嵌入图片；
- 管理界面提供浏览、搜索与编辑，不提供历史版本界面。

本文描述用户能够获得的功能，不限定检索算法、数据库或模型实现。存储形态、工具字段与索引语义以 `docs/contracts/personal-kb.md` 为准；长期记忆与每轮上下文的规则见 `docs/memory-spec.md`。本文不是已实现功能清单。

## 1. 产品目标

让用户把需要按原文查回的资料交给 Pebble 保管，之后直接提问就能得到基于资料的正确回答；资料随使用逐步整理成主题，助手对用户的人物、项目和事务了解得越来越完整。资料本身是用户能直接打开、修改和整理的文件，不锁在系统里。

用户可以直接说：

- “把这份会议纪要存起来。”
- “星云项目这次验收的代号是什么？”
- “张老师上次邮件里约的时间，记到资料里。”
- “星云项目最近进展到哪了？”
- “把项目资料按学期整理一下。”
- “刚才删掉的那份课程笔记找回来。”
- “这份资料改之前写的是什么？”

用户不需要选择检索方式、记住文件放在哪里，也不需要懂 Git。

## 2. 资料库在整体中的位置

Pebble 的个人上下文分为三层（与 `memory-spec.md` 第 2.2 节一致）：

| 层 | 是什么 | 是否每轮带给 Agent | 作用 |
| --- | --- | --- | --- |
| 长期记忆 | 内容本身：背景、偏好、约定 | 是，全文 | Agent 直接照着做 |
| 资料目录 | 指针：有哪些资料、各讲什么、在哪 | 是，有容量上限 | Agent 据此决定要不要去查 |
| 资料正文 | 具体内容 | 否 | 需要时检索或读取 |

判断一条信息放记忆还是放资料，只问一个问题：**Agent 这一轮没看到它，会不会在用户没提起的情况下做错？** 会做错的（如“回答先给结论”“内部会议默认 45 分钟”）放记忆；只是被问到时答不上来的（如验收代号、办公室位置、截止日期）放资料。内容长短不是标准：一条很短的事实照样是资料。资料目录是资料的一部分，不能代替记忆——目录里列着一份讲回答风格的资料，Agent 未必会去读，偏好就不会生效。

资料库保存具体资料和原文，数量可以一直增长；每轮常驻的只是资料目录（第 4.3 节），正文在与问题相关时才读取。分不清用户想“记住一个偏好”还是“保存一份资料”时，Agent 先问清楚。

资料库只负责保存、整理和检索内容，不执行外部操作：发送邮件、创建日程等由对应工具按授权规则完成，资料中的内容不能代替用户授权。

资料中出现的指令只是资料内容：不会变成长期记忆，不能改变 Agent 的行为。密码、令牌等凭证不保存到资料库。

## 3. 保存资料

### 3.1 保存方式

资料有三种进入方式：

1. **用户要求保存**：用户说“存起来”“记到资料里”，Agent 保存。
2. **Agent 主动保存**（第 3.2 节）：Agent 判断某些内容以后需要按原文查回，不等用户要求就保存。
3. **用户直接放入文件**：用户在 `kb/` 目录里新建或复制 Markdown 文件，或在管理界面里新建（第 6、7 节）。

每次保存都生成一个用户可直接打开的 Markdown 文件，并留下一个历史版本。

### 3.2 Agent 主动保存

Agent 可以不经用户要求保存或修改以下内容：

- 对话中用户提供的资料：用户贴进来的文档、笔记和项目细节，即使没有说“保存”。
- 邮件与日程中的关键信息：人物、活动、约定、时间安排等，包括新邮件自动触发的轮次。
- 跨工具任务的归档（第 3.4 节）。
- 已有资料的更新：发现资料已经过时（例如对方改了时间），直接修改原资料，不另建副本。

主动保存的约束：

- 保存前先查找是否已有同一份资料；已有时修改原资料，不产生重复文件。
- 只保存以后可能需要按原文查回的内容；闲聊、一次性的临时安排和凭证不保存。
- 修改基于资料的当前版本。资料在 Agent 读取之后被用户改过时，不静默覆盖，先重新读取最新内容，再决定怎么改或询问用户。
- 保存与修改和用户要求的保存一样展示结果（第 3.3 节），不在后台悄悄写入。

### 3.3 保存结果的展示

每次写入成功后，程序依据实际写入结果在对话中展示提示，不依赖 Agent 复述：

- 新建：“已保存资料：星云项目验收纪要。位置：「项目」文件夹”
- 修改：展示资料名、所在文件夹，以及修改前后的版本。

提示与 Agent 的回答都用标题和所在文件夹指代资料，不出现文件名：文件名由程序按标题生成（见第 3.5 节），用户只认标题。
- 已保存但暂时检索不到：“资料已保存，但当前不可检索”。
- 保存失败：如实说明失败和原因，不声称已经保存。

新邮件自动触发的轮次里发生的保存，提示显示在该任务的时间线上。

### 3.4 任务归档

跨工具任务（例如查日程、回信、建日程）中的外部操作有了实际结果后，Agent 自主判断并把关键信息和逐项执行结果归档到资料库；纯问答、闲聊或只起草未确认的任务不归档。归档便于以后查回“当时做了什么、结果如何”。

- 原始内容（邮件原文摘录、日程信息）与模型总结分节保存，不混写，避免把总结当成原文。
- 执行结果以实际执行记录为准：没有发送成功的邮件不写成“已发送”，结果不确定时写明不确定。
- 归档完成后展示保存位置。

### 3.5 资料格式

资料库只收录 Markdown。用户给出 PDF、邮件附件、网页等其他格式时，由 Agent 提取需要的文字存成 Markdown；原始文件不存入资料库。

例外是正文里的图片（Phase 6）：用户在管理界面把图片粘贴或拖进正文，图片随资料一起保存。插入时自动生成一段图片说明（有文字的图尽量转写要点），用户可以修改；Agent 通过这段说明检索和理解图片，不直接看图。

每份资料有一句话说明（例如“二期验收结论、代号与遗留问题”），它出现在资料目录里，决定 Agent 以后能不能想到去读这份资料，也和标题、正文一样可以被检索到：Agent 保存或修改资料时填写，用户也可以在管理界面或文件里修改；管理界面可以按标题和正文让轻量模型起草说明，用户确认后再保存。没有说明的资料在目录里只显示标题。

资料按目录组织，目录由 Agent 按内容选择，不强制固定的分类法；资料不带标签。用户没有指定位置时，Agent 自行选择合适的目录；不确定时放在资料库根目录。

标题就是资料的名字。文件名取标题，同一文件夹里重名时依次编号（“DVM 2.md”）；之后改标题，文件名随之更新，文件夹不变。用户在文件系统里自己起的文件名不受影响，直到下次改标题。

## 4. 查找资料并回答

### 4.1 回答依据

- 问题涉及资料中的具体事实时，Agent 先检索资料库，再读取原文确认后作答；检索摘要不单独作为回答依据。
- 问题涉及某个人物、项目的整体情况时，Agent 可以先读对应主题页（第 8 节）获得概况，需要细节时再检索和读取具体资料。
- 用户可以用关键词、编号、英文或自然语言提问；中文连续文本、英文单词和编号都能检索到。
- 检索不到依据时如实说“资料库里没有找到”，不凭印象或长期记忆编造答案。
- 多份资料互相矛盾时，说明存在冲突以及各自的说法，不自行挑一个当成事实。
- 问到资料的旧内容时（“改之前写的是什么”），读取对应的历史版本回答，并说明是旧版本。

### 4.2 不展示来源与读取记录

- 回答下方不附来源卡或引用列表。
- 程序不记录也不展示 Agent 读取了哪些资料；只有写入（保存、修改、删除、移动、恢复）的结果会展示给用户。
- 用户问“那份纪要放在哪”这类位置问题时，Agent 按查到的结果正常回答。这是在帮用户找资料，不是来源展示。

资料系统内部仍保留定位原文的信息（文件路径、行号、版本），只用于工具读取原文与历史版本，不展示给用户，也不作为出处记录。

### 4.3 资料目录

资料正文不可能每轮都带给 Agent，所以每轮常驻一份程序生成的资料目录，告诉 Agent 库里大致有什么：

```text
资料库共 23 份资料；需要细节时用 kb_search 检索，或用 kb_read 读取原文。
- 项目/星云/（8 份）
  - 星云项目验收纪要：二期验收结论、代号与遗留问题
  - 周会纪要：运维预算与负责人安排
  - 另有 6 份
- 课程/（5 份）
  - GSE 实验一要求：第一次实验的任务要求与提交方式
  - ……
```

- 每份资料一行：标题加一句话说明，按所在目录分组。
- 目录由程序每轮从资料文件现算，不是一份需要维护的文件：用户改标题、改说明、移动或删除文件后，下一轮就反映出来。
- 目录有容量上限。资料多时最近更新的目录与资料优先列出，列不下的合并成“另有 N 份”或“另有 N 个目录未列出”；列不出的资料仍可检索到。
- 目录只是指针。回答具体事实仍要读取原文；Agent 可以依据目录直接读取对应资料，也可以检索。
- 首版不在每轮回答前自动预先检索资料；实测发现 Agent 经常漏查时，再考虑增加回答前的预检索。

## 5. 修改、删除、移动与恢复

### 5.1 修改

- 用户或 Agent 修改资料时改动原文件，资料身份保持不变，每次修改留下历史版本。
- Agent 做局部修改时只改动涉及的行，资料其余内容逐字不变；只有重写大部分内容时才整篇替换。
- 修改结果展示资料名、所在文件夹和修改前后的版本（第 3.3 节）。

### 5.2 删除与移动需要先确认

- Agent 删除资料、移动资料、批量整理目录之前，先在对话中说明要做什么（涉及哪些文件、移到哪里），得到用户明确同意后再执行。
- 用户在同一条消息里已经明确要求（“把这份删掉”“移到课程目录”）时，视为已经同意。批量整理仍需先列出方案并确认。
- 用户没有回复或意思不明确时不执行。
- 删除后文件从 `kb/` 目录移除，不再被检索到；历史版本保留，可以恢复。
- 移动或改名后资料身份不变，历史版本仍能找到这份资料。改标题（文件名随之更新，文件夹不变）属于修改，不需要先确认。

### 5.3 恢复

- 用户在对话中要求找回已删除的资料，或把资料恢复到某个旧版本时，Agent 查找历史版本并恢复。
- 恢复本身也产生一个新版本，不改写已有历史；恢复结果展示位置与版本。
- 有多个可能的候选（例如同名资料、多个旧版本）时，先向用户确认恢复哪一个。

## 6. 用户直接改动文件

资料是普通 Markdown 文件，用户可以用任意编辑器或文件管理器直接编辑、新增、移动和删除。

- 程序自动发现这些改动，纳入版本历史并更新检索，最迟在下一次检索前生效；用户不需要手动同步或操作 Git。
- 用户移动或重命名文件后，程序识别出是同一份资料，历史版本继续有效，不当成“删掉一份、新建一份”。
- 用户自己新建、没有资料标识的 Markdown 文件同样收录；程序只补充必要的标识信息，不改动正文。
- 用户正在改的文件与 Agent 的修改冲突时，以用户的改动为准：Agent 的修改不静默覆盖用户内容，重新读取后再处理。
- 用户直接删除的文件不再被检索到，历史版本保留，可以通过对话恢复。

## 7. 资料管理界面

电脑和手机浏览器都可以使用资料管理界面，无需命令行：

| 能力 | 说明 |
| --- | --- |
| 浏览 | 按文件夹逐层查看资料列表（标题、一句话说明与更新时间）与主题页，打开资料阅读正文 |
| 搜索 | 按关键词搜索，结果显示资料标题与命中片段，点击打开对应资料 |
| 编辑 | 在当前文件夹里新建资料或文件夹；编辑、移动、重命名和删除资料（重命名即改标题）；标题与一句话说明用表单，正文用所见即所得编辑器，可粘贴或拖入图片（Phase 6） |

- 界面操作由用户本人发起，等同于用户直接改动文件：删除时界面自身给出确认，保存后留下历史版本，并按第 6 节纳入检索。
- 界面与文件是同一份资料：界面里的修改立即反映到文件，文件的修改在界面中可见。
- 资料在打开之后被 Agent 或编辑器改过时，保存不会覆盖，界面提示并让用户重新载入。
- 所见即所得编辑器保存的仍是 Markdown，可能按统一格式重新排版被编辑的正文（例如表格对齐）；只打开不编辑、或只改标题与说明时，正文原样保留。
- 正文里的数学公式写作 `$…$`（行内）与 `$$…$$`（独占一段），界面显示为排版后的公式，点击后修改源码；对话里的回复同样按公式显示。金额这类 `$5 到 $10` 的写法不算公式，保持原文。
- 界面不提供历史版本、差异对比与恢复入口；这些操作在对话中完成（第 5.3 节）。
- 界面不展示 Agent 的读取记录。

## 8. 主题页：资料的整理与压缩

资料会不断增加。为了让 Agent 不必每次都从大量零散资料里重新拼出全貌，资料库为长期存在的主题维护**主题页**：人物、项目、课程、组织等。主题页本身是资料库里的 Markdown 文件，与其他资料一样可以阅读、检索、修改，并留有历史版本。

### 8.1 主题页的内容

- 该主题的当前概况：例如项目的目标、当前进展、关键决定与待办，人物的身份、沟通习惯与近期往来。
- 按时间整理的重要变化，保留足够继续工作的要点，不照抄原文。
- 可以列出与该主题相关的资料位置，方便需要细节时深入阅读；不要求逐条标注信息出处。

### 8.2 主题页的维护

- Agent 在保存或修改与某主题相关的资料时，可以同步更新对应主题页；没有主题页的主题出现多次后，可以新建主题页。
- 后台定期整理：与后台记忆回顾同样独立于对话运行，把近期新增或修改的资料与对话中的要点整理进主题页，合并重复内容、更新过时的概况。整理只写资料库，不改长期记忆，不向用户发送通知；主题页的新建与修改仍可在历史版本中查看。
- 用户对主题页的修改优先：整理基于主题页的当前版本进行，不把用户改过的内容改回去；用户删掉的条目不因重新整理自动出现。
- 主题页是整理结果，不替代原始资料：概况与原始资料不一致时以原始资料为准，Agent 回答具体事实时仍读取原始资料。
- 删除主题页不影响原始资料；需要时可以重新整理生成。

### 8.3 主题页在资料目录中

主题页和其他资料一样出现在资料目录里（第 4.3 节），标题与一句话说明让 Agent 知道有哪些主题可读，不再单独维护主题目录。

## 9. 使用示例

### 9.1 保存、提问与更新

1. 用户贴入一份验收纪要，说“帮我存一下”。Agent 保存，对话显示“已保存资料：星云项目验收纪要。位置：「项目」文件夹”。
2. 用户新建会话问：“星云项目这次验收的代号是什么？”Agent 检索并读取原文，回答“NEBULA-3390”，回答下方没有来源卡。
3. 用户在编辑器里把代号改成 NEBULA-3391 并保存文件。
4. 用户再问同一个问题，Agent 回答“NEBULA-3391”。
5. 用户问：“改之前是什么？”Agent 读取历史版本，回答旧代号是 NEBULA-3390。

### 9.2 邮件信息的主动保存与整理

1. 新邮件自动触发任务：张老师约下周三下午讨论课程安排。Agent 起草回信待用户确认，同时把约定信息保存到资料库；时间线上显示保存位置。
2. 张老师来信改到周四。Agent 修改原资料，不新建副本，时间线上显示修改前后的版本。
3. 用户说：“把课程相关的资料都整理到‘课程’目录下。”Agent 列出要移动的文件和目标位置，用户同意后执行，并展示移动结果。
4. 用户说：“那份旧的课程安排不要了，删掉。”Agent 删除，并说明历史版本仍保留。
5. 一周后用户说：“把删掉的课程安排找回来。”Agent 恢复资料并展示位置。

### 9.3 主题页

1. 用户在几周里陆续保存了星云项目的验收纪要、周会纪要和几封相关邮件的要点。
2. 后台整理新建主题页“星云项目”，汇总目标、当前进展、关键决定与待办；资料目录出现一行“星云项目：二期验收与复验安排”。
3. 用户新建会话问：“星云项目最近进展到哪了？”Agent 从资料目录得知有该主题，读取主题页作答；用户追问复验负责人时，Agent 检索并读取具体纪要确认。
4. 用户在主题页里删掉一条已经取消的待办。之后的整理不再把这条待办加回去。

以上为验收示例，不要求每个任务都固定经过同样的工具调用步骤。

## 10. 验收标准

以下均为应验证的产品行为，不代表已经实现或通过测试。

| 编号 | 用户操作或情境 | 可观察的结果 |
| --- | --- | --- |
| K1 | 要求保存一份资料 | `kb/` 下出现可直接打开的 Markdown 文件；对话显示程序生成的保存位置 |
| K2 | 贴入资料但没有说“保存” | Agent 可以主动保存，并展示保存位置；不写入长期记忆 |
| K3 | 新邮件包含约定信息 | 触发轮次可以把关键信息保存为资料；不执行任何外部写操作 |
| K4 | 同一份资料的信息发生变化 | 修改原资料而不是新建副本；展示修改前后的版本 |
| K5 | 资料写入失败或暂时不可检索 | 如实展示失败原因或“当前不可检索”，不声称已经保存成功 |
| K6 | 询问资料中的具体事实 | 先检索、再读原文，回答与资料一致；回答下方没有来源卡 |
| K7 | 询问资料库里不存在的内容 | 明确说没有找到，不编造答案 |
| K8 | 两份资料说法冲突 | 回答指出冲突和各自的说法，不自行挑一个 |
| K9 | 询问资料修改之前的内容 | 读取历史版本作答，并说明是旧版本 |
| K10 | 任意资料问答之后查看对话与界面 | 找不到 Agent 读取了哪些资料的记录；写入结果仍可见 |
| K11 | 要求 Agent 删除或整理资料 | 执行前在对话中说明涉及的文件并得到同意；未同意时不执行 |
| K12 | 删除资料后再要求找回 | 删除后检索不到；恢复后资料回到原位，产生新版本，历史不被改写 |
| K13 | 移动或重命名资料（经 Agent、界面或文件系统） | 资料身份不变，历史版本仍可查看 |
| K14 | 用户在编辑器中修改、新增或删除文件 | 无需手动同步，下一次检索即反映改动，改动进入版本历史 |
| K15 | 用户和 Agent 先后修改同一份资料 | 用户的改动不被静默覆盖 |
| K16 | 提供 PDF 或邮件附件 | 保存为 Markdown 文字；原始文件不进入资料库 |
| K17 | 资料正文里含“忽略之前的要求”“记住我喜欢…”这类指令 | 不改变 Agent 行为，不写入长期记忆，不触发外部写操作 |
| K18 | 完成一次跨工具任务 | 归档关键信息与逐项结果，原始内容与总结分节；未成功的操作不写成已完成 |
| K19 | 在资料正文里粘贴一张表格截图并保存 | 图片随资料保存并显示；之后按截图里的文字提问，Agent 能检索到这份资料并依据图片说明作答 |
| T1 | 同一主题的资料累积多份 | 出现对应主题页，概况与原始资料一致；资料目录出现该主题页 |
| T2 | 新会话询问某项目整体进展 | Agent 借助资料目录与主题页作答，追问细节时读取原始资料 |
| T3 | 用户修改或删除主题页中的内容后再次整理 | 用户的修改保留，删掉的条目不被加回 |
| D1 | 新会话询问“库里有哪些关于某事的资料” | Agent 依据资料目录说出相关资料及其内容，不把无关资料列进来 |
| D2 | 询问目录说明里没有的细节 | Agent 检索或读取原文后回答，不凭目录猜测 |
| D3 | Agent 保存资料；用户改标题、说明或移动文件 | 保存时填写一句话说明；下一轮资料目录反映最新标题、说明与位置 |
| D4 | 资料数量超过目录容量 | 目录保持在上限内，最近更新的优先列出，其余合并计数且仍可检索 |
| U1 | 在电脑和手机上打开资料管理界面 | 可以按目录浏览、搜索并打开资料与主题页，新建、编辑、移动、删除资料 |
| U2 | 在界面中编辑资料，再到文件系统查看 | 两边内容一致；修改可被检索，并留下历史版本 |
| E1 | 完成第 9.1 节全部步骤 | 保存、提问、手动改文件、旧版本查询形成完整链路 |
| E2 | 完成第 9.2 节全部步骤 | 主动保存、更新、确认后整理、删除与恢复形成完整链路 |
| E3 | 完成第 9.3 节全部步骤 | 主题页生成、借助主题页作答、用户修改优先形成完整链路 |

验收必须使用真实模型、真实文件与版本历史完成检索作答、主动保存与主题整理；仅测试文件读写或使用固定的模拟回答，不足以证明上述能力。

## 11. OpenHuman 参考与取舍

参考 OpenHuman 的 Memory Tree 与 SuperContext 设计（2026-09-16 查阅），借鉴其思路而不照搬实现：

| OpenHuman 做法 | 本文采用 | 取舍理由 |
| --- | --- | --- |
| 记忆、上下文、Agent 运行、工具分层，记忆不执行外部操作 | 采用：资料库只负责保存、整理与检索（第 2 节），每轮上下文装配单独负责 | 边界清楚，资料增长不影响授权与执行 |
| 小容量常驻状态与按需检索分开 | 采用：长期记忆与资料目录常驻，资料正文按需检索（第 2、4.3 节） | 控制每轮上下文成本 |
| 数据源适配器统一转成 Markdown | 不采用：不从外部笔记应用导入 | 资料来自对话、邮件与用户直接放入的文件，首版不维护外部来源 |
| 分层摘要树（按来源、主题、全局）压缩海量数据 | 改为 Agent 维护的主题页（第 8 节） | 个人规模下分节检索足够；主题页是可读、可改、有版本的 Markdown，不引入用户无法查看的中间结构 |
| 全量同步邮件等外部数据进入记忆 | 不采用：邮件、日程在原服务中按需查询，只保存值得查回的内容 | 避免同步负担、隐私范围扩大与大量噪音 |
| 每个数据块保留出处 | 不采用：内容可查看、可修改即可 | 产品决定，见本文状态说明 |
| 新会话先由只读检索器预先组装上下文 | 暂不采用：由 Agent 依据资料目录自行检索（第 4.3 节） | 避免每个会话额外的模型调用；按实测再决定 |
| 独立的小容量目标文件，每轮常驻 | 不采用：长期目标保存在 `USER.md` | 现有长期记忆已覆盖，第一版不增加文件与写入目标 |
| 以数据库为准，Markdown 为生成结果 | 不采用：以 Markdown 文件为准，索引与目录是可重建的派生数据 | 保证用户能直接编辑并有版本历史 |

参考资料：

- [OpenHuman Memory Tree](https://github.com/tinyhumansai/openhuman/blob/main/gitbooks/features/obsidian-wiki/memory-tree.md)

## 12. 不在本文范围内

- 原始二进制文件（PDF 等）的保存与预览；图片只作为资料正文的插图保存（第 3.5 节）。
- 向量检索、知识图谱或第三方知识库服务；本文只要求检索结果正确，不限定检索方式。
- 资料与记忆的出处记录。
- 从外部笔记应用（如熊掌记、Obsidian）导入资料。
- 资料标签；资料按目录组织，检索命中标题、分节标题、一句话说明与正文。
- 多用户共享资料或远端同步；资料只保存在单用户实例的数据目录中，版本历史不推送远端。
- 将已有长期记忆中的旧资料批量迁移进资料库；迁移留待后续逐条核对后再做。
- 邮件发送、日程创建等外部写操作的授权规则，仍以 `v1-spec.md` 与对应接口约定为准。
