# Qoder 个人资料库 Phase 2 验收记录（2026-09-16）

## 结论

Pebble 使用真实 Qoder 模型完成了资料库第二阶段闭环：模型先检索资料库、再读取原文，回答依据
可定位到文件的真实行号与提交；程序把每次成功读取的引用与原文片段记入时间线，展示在回答下；
资料更新后新回答使用新版本，旧回答仍保留旧版本原文；两份资料冲突时回答列出各自来源；查不到
依据时不编造答案也不产生虚假来源。

验收使用 `qodercn-agent-sdk==1.0.14` 和其捆绑的 Qoder CLI CN 1.1.38。

## 真实验收结果

| 场景 | 输入与检查 | 结果 |
| --- | --- | --- |
| 检索后读原文 | “资料库里星云项目这次验收的代号是什么？” | 模型调用 `kb_search`（两次查询）后 `kb_read`，回答给出 `NEBULA-3390` |
| 来源与真实读取一致 | 比对来源卡的路径、行号、提交与保存结果 | 路径为 `kb/项目/星云验收.md`，提交等于保存时产生的提交 |
| 更新后新版本 | 更新该资料后在同一问题下重新提问（全新会话） | 回答改为 `NEBULA-3391`，来源指向新提交与新原文 |
| 旧回答保留旧版本 | 资料更新后重新读取第一次提问的时间线 | 来源（提交、行号、原文片段）与更新前完全一致 |
| 资料冲突 | 追加一份代号不同的资料后提问 | 回答同时列出 `NEBULA-3391` 与 `NEBULA-3392`，来源包含两份不同文件 |
| 查不到依据 | 询问不存在的代号 `NEBULA-0000` | 回答明确说明没有该记录，来源中不含该代号，未产生虚假引用 |

第一次提问的实际工具轨迹：

```json
{
  "searches": ["星云项目 验收", "NEBULA 代号"],
  "reads": ["document:kb/项目/星云验收.md", "document:kb/项目/周会.md"]
}
```

该轨迹里模型按引用以外的参数读取了整篇资料（资料很短）。检索与读取都真实发生，来源记录取自
实际读取结果，因此验收只断言“先检索、再读取、来源与文件一致”，不规定读取用引用还是整篇——
设计第 9 节明确不要求固定调用顺序。

## 自动化验证

- `tests/storage/test_kb_index.py`：中文、英文、编号、标签、来源类型与 1–2 字关键词检索；二级
  标题分节、无标题正文、代码围栏、空分节、结果数量与字段优先级排序；保存与更新只替换受影响
  的资料；索引缺失、损坏、结构版本变化与 Git tree 不一致时重建；重建失败时拒绝返回旧结果；
  引用按行号切出原文，越界、身份不匹配、路径越界与不存在的提交被拒绝；更新后旧引用仍能读到
  旧原文。
- `tests/gateway/test_kb_sources.py`：只有成功的 `kb_read` 产生来源，检索摘要与失败的读取不产生；
  来源挂在该轮最后一段回答上；同一轮重复读取同一版本与行号只记一次；重复读取时间线保持一致。
- `tests/storage/test_db.py`：schema 11 迁移保留既有时间线，来源表按 `run_id + commit + path +
  行号` 唯一，删除任务时一并清理。
- 前端：`SourceCard.test.tsx` 覆盖来源卡字段、多条来源顺序、长路径与长原文换行、无来源不渲染。

## 可重复执行

在仓库根目录运行：

```bash
uv run --project server python -m tests.acceptance.qoder_kb_search
```

脚本显式调用真实模型并消耗账号额度，因此不进入普通 pytest。它同样使用临时数据目录、真实文件、
本地 Git、SQLite 与 MCP HTTP；Gmail 使用替身，Calendar 未装配，全程没有外部账号读写。

## 验证边界

- 不验证用户直接在文件系统里改动、移动或删除后的自动同步（Phase 3），也不验证资料管理界面、
  版本差异视图与读写记录面板（Phase 4）。
- 索引只收录与 Git 版本一致的文件；本次验收中的资料都由应用写入并提交，未覆盖“用户改完未提交”
  的检索表现，该行为由单元测试覆盖。
- 检索为关键词全文检索，不做语义召回、自动摘要或知识图谱。
- 未迁移任何现有长期记忆内容，也未改动每轮记忆判断与后台回顾流程。
